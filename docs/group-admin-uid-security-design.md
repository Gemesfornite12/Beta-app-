# Draft: UID-based RTDB group administration and authorization

**Status:** design only; not a rules or data migration. Audited Beta `main` at `e3e6fe4ac1ba82b90c255060de87488fbce49025` and Flutter Stage 3 at `ee17d423b63b4465d70262e2f3c844d818d38458`. No Firebase emulator/live database was accessed.

## Decision: do not change `database.rules.json` yet

The current `chats` rules grant authenticated users a read at `/chats` and a write at `/chats/{chatId}`. Removing the latter without first refactoring all writers would break existing parent-level updates; replacing it with broad child grants would still permit unsafe message and membership changes. The current membership data also cannot support a safe UID membership check: Kotlin serializes `members` as a list of objects identified by email, and direct chats use the same email-oriented shape. RTDB rules cannot safely use those email strings as authorization, and must not infer ownership of a legacy chat from `creatorEmail`.

This branch intentionally changes no rules, app code, tests, or Firebase data. Keep the existing `creatorEmail` and email/member parsers for display/read compatibility, but do not use them to authorize access. Legacy chats lacking UID membership remain inaccessible under any future UID-only rules until explicitly migrated from trusted identity mappings; do not auto-grant access by matching email.

## Audited current schema and write paths

### Kotlin Beta (`database.rules.json`, `RealtimeDatabaseService.kt`, `OmniViewModel.kt`, `Models.kt`)

- Channel metadata includes `id`, `name`, `description`, `iconEmoji`, `isDirect`, `isGroup`, `groupPhotoUrl`, `creatorEmail`, `creatorName`, `members`, `isDeleting`, `lastUpdated`, and optional `pendingDeletionTimestamp`. A member object has `email`, `name`, `role`, `canSendMessages`, `canSendMedia`, `canInviteMembers`, and `avatarUrl`; it has no stable member UID. Group creation currently sets `creatorEmail` and an owner member only.
- `saveOrUpdateChannel()` uses `updateChildren()` at `/chats/{channelId}` to write the channel metadata and the entire `members` list. This is used for direct-chat creation, group creation, metadata edits, add/remove/leave, permission updates, deletion scheduling/cancellation. `deleteChannel()` removes `/chats/{channelId}`. Several administrative restrictions exist only in ViewModel/UI checks comparing email; those checks are not authorization boundaries.
- `sendMessage()` writes a whole object at `/chats/{channelId}/messages/{messageId}`. It includes `senderId` from `FirebaseAuth.currentUser.uid` plus `messageId`, `pushEnvironment`, `senderName`, `senderEmail`, `text`, `timestamp`, attachment/media/call fields, `reactions`, `deliveryStatus`, `sentTimestamp`, `deliveredTimestamp`, `seenTimestamp`, and `seenBy`. It separately updates `/chats/{channelId}` fields `lastMessageText`, `lastMessageTimestamp`, `lastMessageSender`, and `lastUpdated`.
- `deleteMessage()` removes a whole message. `updateReactions()` writes one comma-separated `reactions` string at `/messages/{messageId}/reactions`; it does not record which UID owns a reaction. No RTDB content-edit operation was found in the audited Beta chat writer/ViewModel paths; do not assume one exists or permit it without specifying a separate write contract.
- Current channel/member reads are unfiltered at `/chats`, then filtered client-side. Tightening per-chat reads therefore also requires a UID-scoped channel listing/index; otherwise group discovery/listening will fail or retain an overbroad read.

### Flutter Stage 3 (`lib/chat/chat_repository.dart`, `lib/chat/chat_message_schema.dart`)

- `ChatChannel` parses legacy `creatorEmail` and list-valued `members`; `includesEmail()` authorizes only a client-side display/filter decision. `loadChannels()` reads `/chats` and filters by email locally.
- Text, attachment, and voice-note serializers write messages at `/chats/{channelId}/messages/{messageId}` with `senderEmail`, but currently omit Beta's `senderId`. `toggleReaction()` updates the whole `reactions` string at the message path. `_updateChannelPreview()` updates the four parent preview fields listed above.
- This Stage 3 repository has no group create/edit/member-admin writer. Before enforcing UID rules, update the Dart typed channel/member/message schema and all writers to match the approved UID contract; do not treat this read-only prototype as a complete audit of any other branch.

## Required target contract before rules can be drafted

1. **Channel identity and membership:** add immutable `creatorUid` to newly created groups and store members in a rules-addressable map, e.g. `membersByUid/{uid}` (member data may retain email/name/role/capabilities for display). Require `membersByUid/{auth.uid}` for participant operations and `creatorUid == auth.uid` for creator-only operations. Keep `creatorEmail` and legacy `members` only as compatibility/display fields. Direct-chat participants need the same UID-keyed representation. Never authorize using email alone.
2. **Channel listing and reads:** replace whole-root `/chats` reads with an explicit UID-scoped index such as `/userChats/{uid}/{chatId}: true`, kept consistent with membership, and apply per-chat read checks against `creatorUid`/`membersByUid`. Refactor Kotlin and Flutter channel discovery/listeners before removing root read access; RTDB rules do not filter an unscoped root read into per-user results.
3. **Message identity:** require the immutable message `senderId` to equal `auth.uid` on creation. Add `senderId` to Flutter's text/attachment/voice serializers and typed `ChatMessage` model. Preserve `senderEmail` only for display/compatibility. Validate message ID/channel ID and define immutable fields. A future content-edit operation needs an explicit sender-only contract; none was identified in the audited writers.
4. **Message reactions and delivery:** replace the shared string reaction field with per-UID records (for example `/messages/{id}/reactionsByUid/{uid}`), so users can modify only their own reaction, while retaining legacy string parsing for display. Define delivery/seen writes by UID (for example per-recipient records) rather than allowing clients to rewrite whole messages or a shared `seenBy`/status field. Existing `deliveryStatus`, timestamp and `seenBy` fields need an explicit allowed-writer matrix.
5. **Delete and metadata paths:** split parent-level `saveOrUpdateChannel()` into narrowly scoped writes/transactions. Specify which writes are allowed for participant self-leave, creator add/remove/permissions/metadata/deletion, direct-chat creation, message deletion, and previews. Protect immutable `creatorUid`, prevent members from adding themselves or replacing the whole membership map, and ensure parent deletion cannot bypass those checks. Preview writes need a defined participant-only contract and validation, not blanket access to `/chats/{chatId}`.
6. **Legacy migration:** retain tolerant parsing for absent UID fields. Before a UID-only rules rollout, create a separately reviewed migration that adds verified UID mappings and `creatorUid`/membership entries using trusted account identity—not email-only client claims. No migration, live data write, or automatic legacy authorization is included here.

## Tests and rollout gates

After the schema and path refactor is approved, add Realtime Database Emulator rules tests for: creator allowed to administer and non-creator denied; listed participant allowed to read/write permitted message paths; nonparticipant denied; caller cannot forge another sender UID, mutate another member, replace creator UID, alter another user's reaction/delivery record, or delete another sender's message; legacy email-only membership denied. Include the existing direct-chat and group metadata operations in these tests. Preserve `calls`, `calls_test`, and `social_test` rule sections exactly when rules are eventually changed. Do not deploy or write production RTDB data without a separate explicit authorization.
