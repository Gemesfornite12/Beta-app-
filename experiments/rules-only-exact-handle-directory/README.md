This is an isolated candidate based on `Gemesfornite12/Beta-app-` `main` at the experiment's parent commit. It adds a new `/social_test/memberDirectory` sibling and leaves the legacy `/social_test/directory` and all chat rules unchanged. It is not the project's active `database.rules.json` and is not approved for deployment.

## Finding: a safe rules-only contract is possible, with a staged transition

Canonical records are `/social_test/memberDirectory/byHandle/{normalizedHandle} = {uid, handle}`. The private single-valued reverse reservation is `/social_test/memberDirectory/byUid/{uid} = normalizedHandle`. The reverse slot is the one-handle-per-UID lock; the canonical handle child is the one-UID-per-handle compare-and-create point. Auth UID is derived solely from `auth.uid`/the UID path and profile key/value, never a client-supplied owner argument.

The reservation workflow is deliberately staged, with opt-in enforced by the rules as well as requested by the UI:

1. After the user explicitly opts in and the client normalizes/validates the handle, run a transaction at the caller's exact `byUid/{auth.uid}` slot, changing only `null -> handle`. Rules require the authenticated UID's profile to contain the matching `.uid`, `/social_test/preferences/{auth.uid}/memberDirectoryOptIn` to be exactly `true`, a normalized handle, and no already-claimed canonical handle.
2. Create `byHandle/{handle}` only when it is absent, the new record's UID is `auth.uid`, the same profile UID binding and exact-`true` opt-in still hold, and the committed reverse slot equals that handle. Use a transaction at the canonical handle child (or a create-only write and handle permission-denied races); only one owner can create it. If a retry finds the caller's same reverse slot, treat it as an idempotent reservation and continue/recover the canonical create only while opt-in remains true; if it finds a different handle, stop. If the canonical record already exists, read that exact child and treat it as success only when its UID and normalized handle match the caller/request.
3. To opt out and revoke an active mapping, first write `false` to the user's own `memberDirectoryOptIn` preference; this immediately blocks new reservations and canonical creates. Then delete the canonical mapping as its owner, followed by the private reverse slot. The reverse slot cannot be cleared while its canonical mapping is still owned by that UID. If the user has only an incomplete/stale reservation (the canonical record is absent or belongs to someone else), the user can clear that private slot even after opting out. If interrupted after the mapping delete, the remaining private slot is recoverable by clearing it; if interrupted before that delete, finish the mapping deletion first. A user cannot change an occupied reverse slot or hold two active mappings.

A single multipath update that tries to create both records from an empty state is *not* the authorization primitive here: child-level `root` checks observe the pre-write state, so the new reverse pointer cannot authorize its sibling handle create in that same update. The design relies on a committed per-UID RTDB transaction, then a separate rules-checked canonical create. This permits temporary private reservation/cleanup state, but never permits two active handles for one UID or two owners for one handle. Directory mappings are not a distributed atomic pair during that short interval; clients must handle/recover stale reservations idempotently. This is a deliberate, fail-closed tradeoff, not an assertion that transactions are unnecessary.

Exact point reads are allowed only on authenticated `byHandle/{handle}` records; no read grant exists at `memberDirectory`, `byHandle`, or collection levels. `/byUid/{uid}` is readable only by that UID. Records contain only `uid` and normalized `handle`. Exact reads remain enumerable by probing predictable strings; the design does not claim otherwise. Rules require the per-UID preference to equal boolean `true` for reservation and canonical creation, but cannot prove that a human saw or understood the consent dialog; the UI must still obtain explicit opt-in and update this preference. Turning consent off does not itself delete data; follow the revoke order above. Profile existence/UID binding is checked on creation, but deleting a profile or Firebase Auth account does not automatically cascade these RTDB records. Require opt-out/revoke before account deletion or add a trusted deletion-cleanup/retry path if that lifecycle guarantee is required. App Check / rate limits are not implemented here.

Directory lookup only resolves an opted-in UID. It grants no chat membership or write authority. Checked-in `/chats/$chatId/.write = auth != null` is intentionally untouched and remains a separate blocker for secure group authorization.
